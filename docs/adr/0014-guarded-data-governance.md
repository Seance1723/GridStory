# ADR 0014: Data governance uses explicit links and guarded execution

- Status: Accepted
- Date: 2026-08-23
- Task: M6-003

## Context

GridStory has explicit tenant scope, immutable content revisions and audit records, durable identity and asset repositories, logical content portability, native database backup/isolated-restore tooling, worker leases, plugin lifecycle warnings, and framework-neutral adapter boundaries. It does not have an authoritative retention or legal-hold state machine, subject-to-resource linkage, destructive resource processors, customer-managed encryption-key integration, or a placement policy gate. Existing portability exports content rather than a verified subject inventory; identity deprovisioning revokes access without removing direct identifiers; asset expiry metadata is not a deletion policy; and deployment-owned backup retention is not product retention.

M6-003 combines rights workflows, preservation, deletion, encryption keys, and residency. Those concerns interact: a legal hold or processing restriction can override deletion, a data-subject export must not expose another subject, a retention candidate can become ineligible before execution, encrypted output depends on key state and location, and a code rollback cannot restore erased production data. The feature must therefore be useful without claiming that software selects the applicable law or discovers every occurrence of personal data.

## Prior-art comparison

| Approach | Evidence and fit | Decision |
|---|---|---|
| Reuse logical portability, asset expiry, identity deprovisioning, and deployment runbooks | Reuses mature boundaries, but none provides subject linkage, hold precedence, reviewed purge plans, resource effects, or one governance audit trail. | Reuse them as processors/evidence inputs, not as the governance system. |
| Put retention dates and delete methods independently into every repository | Makes local deletion simple, but duplicates policy, permits inconsistent hold checks, and cannot atomically review cross-resource subject effects. | Rejected. Resource repositories expose narrow operations behind one governance service. |
| Delegate all policy and execution to an external privacy/compliance platform | Can provide discovery and case management in a specific deployment, but leaves the self-hosted product unable to enforce holds or prove its built-in resource effects. | Supported later through explicit resource/workflow adapters, not selected as the only implementation. |
| Automatically delete every expired resource on a schedule | Reduces storage, but policy/classification errors, stale candidate sets, external resources, and newly added holds can cause irreversible loss. | Rejected. Scheduling may create plans; deletion requires reviewed, digest-bound approval and revalidation. |
| One scoped governance document, explicit subject/resource links, two-phase plans, and narrow resource/key/placement adapters | Fits the existing optimistic document repositories and worker while keeping framework/cloud details at edges. It is testable, provider-neutral, and honest about unknown external data. | Selected. |
| Store plaintext cloud keys or let GridStory create/disable/destroy customer keys | Gives apparent lifecycle control but makes GridStory a privileged key custodian and turns mistakes into cryptographic erasure. | Rejected. Store opaque references/versions only; adapters may describe, wrap, and unwrap. |
| Treat configured home region as proof of residency and add region routing here | A label cannot prove storage placement, and routing overlaps M8-001 multi-region delivery/failover. | Rejected. Compare declared policy with adapter-reported placement and block disallowed destinations; defer migration/routing. |
| Do nothing / keep manual tickets | Avoids implementation risk but provides no consistent hold dominance, request evidence, tenant-scoped workflow, or safe execution boundary. | Rejected; it fails M6-003 and leaves documented retention/security gaps open. |

## Decision

Create one versioned governance document per complete GridStory scope. It holds bounded retention rules, resource classifications, pseudonymous subject records, explicit subject-to-resource links, legal holds, processing restrictions, data-subject requests, immutable execution plans/receipts, key references, residency policies/status, and ordered hash-chained governance events. In-memory, SQLite, and qualified PostgreSQL repositories persist the same validated document with optimistic versions. Published delivery and caches never read governance documents, and management responses remain private with `no-store`.

GridStory will not infer that an email search found every item belonging to a person. Administrators and import/integration adapters create explicit subject links to supported resources. Access and portable-export requests inventory only those links, label unsupported/external resources, exclude other subjects, and return a deterministic machine-readable package. Request state distinguishes intake, identity verification, review, approval/rejection, restriction, execution, completion, and cancellation. Identity-verification records contain an evidence reference, method, verifier, and time, never identity-document bodies or authentication assertions.

Legal holds are active or released records with matter, reason, custodian, target, and event history. They are not deleted. An active hold dominates retention and erasure. Processing restriction independently blocks destructive/ordinary governed processing while permitting the minimum storage, review, export, or legal-claim operation explicitly allowed by policy. Releasing a hold or restriction never resumes an old purge plan; a new plan is required.

Retention rules do not directly delete data. A scheduler or administrator creates an immutable dry-run plan that records the policy/document versions, exact candidates, stable effect summary, blockers, and a canonical SHA-256 digest. A separately authorized administrator with fresh enterprise reauthentication may approve that exact digest with a reason and a verified whole-system plus external-storage backup reference. The durable worker rechecks scope, plan/policy versions, active holds/restrictions, resource identity/revision, key health, placement, and adapter support immediately before each operation. Any drift blocks the affected item; completed item receipts make retries idempotent. Plans never broaden themselves after approval.

Built-in governed-resource processors cover content aggregates, assets, and identity subjects. Content erasure removes the explicitly targeted aggregate and invalidates its published/cache surfaces. Asset erasure removes metadata and asks the configured storage adapter to remove the exact object/renditions. Identity erasure first revokes sessions and credentials, then removes direct directory/profile identifiers while retaining pseudonymous event identifiers needed for security/audit integrity. Immutable governance, content, and identity events are not silently rewritten. Plugins and external systems must provide a narrow processor and return a receipt; otherwise the plan stays blocked and records operator work rather than claiming completion.

Customer-managed encryption uses a framework-neutral adapter that can describe a tenant-bound key and wrap/unwrap a locally generated data-encryption key. The Node edge provides maintained AWS KMS and Google Cloud KMS wrappers around injected official-client-compatible interfaces. Envelope encryption uses a fresh AES-256-GCM data key per export package, persists/transmits only ciphertext, authenticated metadata, and the wrapped key, and never stores a plaintext data or customer master key. GridStory does not create, rotate, disable, schedule deletion of, destroy, escrow, or recover customer keys; those remain customer/provider operations.

A placement adapter reports current deployment, repository, object, plugin, export, and key locations. A residency policy names allowed locations by resource class and transfer purpose. Framework-neutral gates on governed content, asset, identity, governance, and export writes reject a known disallowed destination and fail closed when a policy requires placement that the adapter cannot attest. A status inventory exposes drift. M6-003 does not copy data, move keys, change database topology, route traffic, or provide multi-region failover; those remain deployment work and M8-001.

Every management operation uses explicit governance read/manage/execute authorization, full scope, redacted bounded telemetry, and ordered security/governance events. Destructive execution requires the exact approved plan and cannot be invoked as an ordinary synchronous CRUD route. Tests may execute destructive processors only against fixtures created inside the isolated test.

## Necessity gate

1. **Traceable:** M6-003 explicitly requires retention, holds, data-subject workflows, CMK adapters, and residency policies; README/security documentation also records product-retention and unbounded-retention gaps.
2. **Not already solved:** portability is content-oriented, identity deprovisioning is access control, asset expiry is passive metadata, database recovery is whole-system/operator-owned, and no shared boundary links subjects or makes holds dominate deletion.
3. **Minimal form:** one scoped document/state machine, explicit links, three built-in processors, two-phase plans, one key contract with two official Node adapters, and placement policy/status are the smallest truthful vertical slice. PII discovery, legal interpretation, key administration, automatic migration/routing, and arbitrary third-party deletion are excluded.
4. **Dependencies justified:** deployments inject maintained official AWS or Google clients behind narrow wrappers, so GridStory does not implement provider authentication, endpoint selection, request signing, or retry. Optional provider SDKs do not enter the framework-neutral core or default browser/server dependency graph.
5. **Rule of three:** one governance boundary serves retention, holds, rights requests, key validation, and residency because they must share blockers and evidence. One resource-processor interface has three immediate built-in implementations; it is not a general rules engine.
6. **Reversible:** contracts, tables, routes, UI, and gates are additive and opt-in; one commit revert disables the feature without rewriting surviving content. Actual erasure is not reversible: production enablement therefore requires coordinated verified backups and the documented provider-specific restore process, while repository verification erases only disposable fixtures.

## Sources that changed the decision

- [GDPR official text on EUR-Lex](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=uriserv%3AOJ.L_.2016.119.01.0001.01.ENG) separates storage limitation (Article 5), erasure and its exceptions (Article 17), restriction (Article 18), portability (Article 20), and transfer safeguards (Article 44); this rules out one unconditional delete state.
- [European Data Protection Board: data-subject rights](https://www.edpb.europa.eu/topics/key-gdpr-concepts/data-subject-rights_en) calls for clear procedures covering access, rectification, erasure, restriction, objection, and portability; the workflow therefore records distinct request types and evidence rather than one generic ticket.
- [U.S. Courts: Current Rules of Practice & Procedure](https://www.uscourts.gov/forms-rules/current-rules-practice-procedure) publishes the current Federal Rules; Rule 37(e)'s preservation/loss model supports rechecking legal holds before destructive execution. The feature is a preservation mechanism, not legal advice about when a duty arises.
- [NIST SP 800-57 Part 1 Rev. 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) treats key material protection, inventory, lifecycle, access, backup, and recovery as explicit key-management concerns; GridStory consequently keeps only key references and avoids key-destruction authority.
- [Google Cloud KMS envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption) distinguishes locally generated data-encryption keys from centrally stored wrapping keys and warns against plaintext DEK storage; exports use a fresh authenticated envelope.
- [Google Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations) documents location-bound key material and exact-location CMEK integration constraints; the key descriptor must expose a provider-attested location.
- [AWS KMS multi-Region key security considerations](https://docs.aws.amazon.com/kms/latest/developerguide/mrk-when-to-use.html) notes that replicated key material changes residency properties and requires region policies/audit evidence; GridStory does not treat a multi-region key as automatically acceptable.

## Safety, rollback, and recovery

The implementation action is limited to additive source/schema/documentation changes and destructive calls against isolated fixtures created by their own tests. It must not erase existing repository/customer data or call live AWS/Google endpoints. Product deletion follows preview, approval, and worker revalidation; any hold, restriction, plan/policy drift, stale reauthentication, missing verified backup reference, unknown/disallowed placement, unavailable key, or unsupported resource blocks completion.

Before enabling production execution, an operator creates and verifies a native backup with `pnpm database:backup -- --output <artifact>` and coordinates object-store, plugin, identity-provider, telemetry, and key configuration backups that the database artifact excludes. SQLite restores to an absent isolated path with `pnpm database:restore -- --backup <artifact> --target <absent-path>`. PostgreSQL restores to an explicitly confirmed empty isolated database using `GRIDSTORY_RECOVERY_TARGET_DATABASE_URL` and `pnpm database:restore -- --backup <artifact> --confirm-target <database>`, followed by integrity/readiness/audit/representative-resource checks and reviewed cutover. A code problem is rolled back with `git revert <M6-003-commit>` and redeployment. A code revert cannot recover erased data.

## Consequences and revisit triggers

- The product gains consistent governance evidence and safe built-in effects, but completeness is only as good as customer classification, explicit links, and installed external processors.
- Human approval reduces unattended automation and makes expired data persist until reviewed; revisit policy-specific auto-approval only after production evidence and a separate T3 decision.
- Retaining pseudonymous immutable security/audit identifiers preserves evidence but requires customers to decide whether their facts and applicable law permit that retention.
- Optional cloud clients stay deployment-owned behind Node-only wrappers; their selected versions, credentials, retry/timeout behavior, production audit, and provider conformance remain deployment evidence.
- Residency status proves only adapter-reported/configured placement. Revisit movement and routing with M8-001, never by expanding the meaning of a policy label.
